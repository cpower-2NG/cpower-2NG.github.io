  • 问题的排查过程与方法论总结见《经验总结》。

1. 实验目标与范围

让一台安装在工作台桌面上的 UR5，通过俯视相机识别桌面上的方块，自主完成定位、规划与抓放。

数据链路为：检测 → 三维定位 → 逆运动学求解 → 轨迹执行 → 夹爪动作 → 搬运 → 放置 → 收工。

范围界定：

  • 覆盖单个或少量方块的点到点抓放。
  • 不涉及 6D 位姿估计、堆叠场景、动态目标与非立方体目标。

2026-10-03 完成首次完整实跑：抓取 1 个、放置 1 个，收工流程正常结束。

3. 系统结构与数据流

D435i(俯视) ──/camera/color/image_raw
             ──/camera/color/camera_info
             ──/camera/aligned_depth_to_color/image_raw
                            │
                            ▼
                 yolo_detector/detector_node
                            │ /detections（像素坐标）
                            ▼
             perception_3d/projector_node      ← 系统中唯一的投影点
                像素 + 深度 经 tf2 变换到 base_link
                            │ /targets_3d
                            ▼
                 grasp_planner/planner_node
                区域筛选(in_zone) → IK(/compute_ik) → 整段护栏
                            │ FollowJointTrajectory
                            ▼
      /scaled_joint_trajectory_controller（受示教器速度滑条缩放）
                            ▼
                 ur_robot_driver（RTDE）
                            ▼
                           UR5

夹爪：planner_node ──pymodbus（串口）──▶ AG-95    独立链路

三点说明：

  1. 投影运算只在 projector_node 一处实现。离线标注必须使用同一条链路的严格逆运算，否则训练标签与在线推理采用不同数学基础。
  1. 规划器不参与投影，仅消费 base_link 坐标系下的 /targets_3d。
  1. 规划器不经由 /move_action 下发轨迹，而是直接调用 /compute_ik 求解位姿后将轨迹发送给关节轨迹控制器。因此 MoveIt 规划场景中是否包含桌面不影响轨迹路径，同时 avoid_collisions=True 也无法阻止机械臂与桌面碰撞；该职责由肘高护栏承担（§6.3）。

4. 坐标系与约定

本节列出该系统中易被误用的四组约定。四者在实际调试中均曾被误处理。

4.1 base_link 与 base 相差 180°（绕 z 轴）

UR 的 URDF 中，机器人自身的 base 帧与 base_link 不是同一坐标系：

$ ros2 run tf2_ros tf2_echo base_link base
  Translation: [0, 0, 0]
  Rotation in RPY (degree) [0, 0, 180.000]

两者在不同环节被分别使用：

使用位置对应坐标系
示教器读数、tcp_pose_broadcasterbase
MoveIt 的 /compute_ik、/compute_fkbase_link

将示教器读取的坐标直接作为 base_link 使用时，机械臂会运动到关于基座中心对称的位置（x、y 同时取反）。实测验证：同一目标点，MoveIt 给出的 tool0 位置为 (-0.42, -0.50, +0.19)，机器人自报 TCP 为 (+0.42, +0.50, -0.01)。

手眼标定采用碰点法，碰点位置从示教器读取，因此标定结果位于 base 坐标系。若要作为 base_link ← camera_link 使用，需左乘 Rz(π)：

R' = Rz(π) · R          t' = Rz(π) · t          Rz(π) = diag(-1, -1, 1)

判定方法：修正后同一物体的 base_link 坐标应为原值的 x、y 取反。此外，光轴与台面法线夹角不应变化（纯 z 轴旋转），实测两侧均为 35.73°。

4.2 camera_link 与相机光学坐标系

  • camera_link：x 向前、y 向左、z 向上。
  • camera_color_optical_frame：z 向前、x 向右、y 向下，针孔投影模型使用该坐标系。

两者之间的固定旋转为：opt_x = −link_y、opt_y = −link_z、opt_z = link_x。

光轴对应 camera_link 的 +x 轴（而非 +z 轴）。取错轴会得到形式合理但整体偏转的结果。

4.3 tool0 与示教器 TCP

  • URDF 与 MoveIt 中的 tool0 指法兰坐标系。
  • 示教器上配置的 TCP 为法兰沿工具 z 轴的偏移。本项目配置为 0/0/200.2 mm，使碰台面时基座 z 读数归零。

两者相差一个沿工具 z 轴的标量偏移，不影响 x、y 分量，因此在排查 x、y 方向异常时可排除该项。

4.4 高度语义：wz 为方块顶面

perception_3d 输出的 wz 为方块可见顶面的高度（俯视深度图获取的是顶面），不是几何中心。

因此 pick_zone 的 z 区间与 place_z 均按“台面高度 + 方块高度”计算：

top = table_z + block_height
pick_zone 的 z 区间 ≈ [top − pad, top + pad]      pad 默认 0.02
place_z            = top

按几何中心计算会产生半个方块高度的偏差，其表现为下降段 IK 全部被拒，即可以抓取但无法放置。

5. 参数体系

参数共三层，需明确覆盖关系。

层来源说明
① 包内默认grasp_planner/config/grasp_planner.yaml全部参数的定义处，共 56 项
② 现场配置planner_params_file:=<文件路径>该文件替换而非叠加包内配置
③ launch 覆盖pipeline.launch.py 按 camera_source 派生见下

关于第 ② 层：launch 中的写法为 parameters=[<指定文件>, {覆盖项}]，包内配置文件不再加载。因此现场配置文件必须完整，缺失项会回退到节点内 declare_parameter 的默认值，而这些默认值按仿真几何设定。

关于第 ③ 层：以下参数由 launch 覆盖，写入第 ② 层无效，因为它们随后端变化：

ik_group · trajectory_action · tool0_to_fingertip · place_release_lift
gripper_backend · table_scene_enabled · carry_objects

这些参数必须保证驱动与 move_group 取到同一个值，否则两侧采用不同的运动学模型且均不报错。

现场配置文件中需要修改的项：

table_plane_z: 0.0                       # 机械臂安装于桌面，台面位于 base 的 z≈0
pick_zone:  [0.40, 0.60, 0.00, 0.50, 0.000, 0.0485]
place_slots: [0.45,-0.25, 0.55,-0.25, 0.45,-0.35, 0.55,-0.35]
place_z: 0.0285                          # 台面高度 + 方块高度（顶面）
ag95_dry_run: false                      # 默认值为 true，此时夹爪仅输出日志不动作

place_slots 有三项启动期检查：

  1. 槽位必须位于 pick_zone 之外，违反时启动失败。该约束即终止机制的实现基础。
  2. 槽位间距不小于夹爪行程（AG-95 为 95 mm），违反时输出告警。
  3. 格式为扁平的 x,y,x,y,...。ROS 2 参数不支持嵌套数组，写成 [[x,y],…] 会导致节点无法启动。

6. 运行流程

阶段 0 · 上位机准备

  • 安装 ros-humble-moveit（15 个子包）。
  • 将运行账户加入 dialout 组（否则无法打开 /dev/ttyUSB0）。
  • 安装 pymodbus 3.x。
  • 释放内存：停止 ollama 与桌面环境。8 GB 内存同时运行 MoveIt、驱动与 YOLO 时余量有限。

阶段 1 · 示教器配置

序号操作原因
1标定或填写 TCP碰点法读取的是工具尖端，示教器显示的是法兰位置；未标定 TCP 会将尖端偏移带入外参
2配置负载与重心未配置可能导致运动过程中触发保护性停机。该要求来自 URControl，与 safety_limits 无关
3Installation → External Control：Host IP 设为上位机在控制箱网段的地址，端口保持 50002URCap 依据该地址回连上位机获取脚本

端口说明：50002 用于机器人向上位机请求脚本，50004 为 reverse interface，两者不可互换。

阶段 2 · 启动驱动并播放 URCap 程序

ros2 launch yolo_bringup real.launch.py robot_ip:=<控制箱IP> ur_type:=ur5 \
    start_pipeline:=false publish_camera_tf:=false gripper_backend:=none \
    carry_objects:=false safety_limits:=true

必须先启动驱动，再在示教器上播放 External Control 程序。顺序相反时，机器人连接 50002 端口会被拒绝；该现象表现为连接被拒绝而非超时，说明网络可达但无监听进程。

播放成功后驱动日志应出现：

[UR_Client_Library:]: Robot requested program
[UR_Client_Library:]: Sent program to robot
[UR_Client_Library:]: Robot connected to reverse interface. Ready to receive control commands.
[URPositionHardwareInterface]: Calibration checked successfully.

核对项（均为只读操作）：

/joint_states 有实际数据 · scaled_joint_trajectory_controller 为 active · /compute_ik 与 /compute_fk 可用 · robotmode: RUNNING · safetystatus: NORMAL · programState: PLAYING

阶段 3 · 手眼标定与漂移检查

标定采用碰点法：拍摄标定板得到 cam←board，用机械臂触碰标定板若干角点得到 base←board，合成为 base←camera。输出文件包含 rms_touch_m 与 reproj_px 两个残差指标。

俯视相机的外参会随时间变化且变化过程无告警输出，实测一天内旋转约 0.945°。原有的基于垂距与夹角的判据无法识别该类变化。检查命令：

python3 scripts/topcam_drift_check.py --old <外参对应的原始帧> --new <当前帧> \
    --info <当前帧的 info.json>
# 退出码 0 表示外参有效；1 表示需要重新标定

该工具基于全幅光流判断：整幅图像同步位移对应相机移动，局部区域位移对应被摄物体移动。使用前提是场景中存在可追踪特征，空白台面无法完成判断。

阶段 4 · 安全包线扫描与区域划分

必要性说明：avoid_collisions=True 无法防止机械臂与桌面碰撞，因为桌面不在 MoveIt 规划场景中；该风险由肘高护栏承担。安全包线的作用是将“试运行观察”转为“按图划分区域”。

python3 scripts/table_safety_envelope.py --table-z 0.0 --retry-seed home \
    --x-min 0.15 --x-max 0.95 --y-min -0.50 --y-max 0.50 --step 0.05 --json /tmp/env.json

扫描范围为桌面网格与四个 tool0 高度的组合，使用 /compute_ik 与 /compute_fk 判断 forearm_link 与 wrist_1_link 的原点是否低于 table_z + guard_margin。

输出分类：碰撞格（应避开）· 不可达格（划入区域无效）· 最大全安全矩形（可直接采用）。

三项注意事项：

  1. 逐格分类结果不可复现：同一位姿连续查询可能返回不同的肘部分支。区域边界应至少保留一格（0.05 m）余量，而其中的矩形区域在多次扫描中保持一致。
  1. 判据仅考虑连杆原点高度，不包含连杆与夹爪本体半径，也不包含相机视野范围。
  1. 最终区域应为“几何安全范围 ∩ 相机可见范围 ∩ 实际操作范围”的交集。

阶段 5 · 现场配置文件

配置内容见 §5。修改后需验证其确实生效：

ros2 param get /grasp_planner pick_zone

返回值应与配置文件一致。

阶段 6 · AG-95 初始化

AG-95 断电后丢失初始化状态。未初始化时的失效无任何日志输出：位置回读恒为 0，写闭合指令后回读值仍为 0，程序判定与目标一致而报成功，但夹爪实际未动作。

python3 scripts/ag95_init_close.py              # 预演模式，不写入任何寄存器
python3 scripts/ag95_init_close.py --go         # 执行初始化

阶段 7 · 分级验证

验证按四个级别依次进行，每级通过后再进入下一级。

级别内容判定依据
① 只读驱动启动、/joint_states 有数据、/compute_ik 可用、/targets_3d 数值合理见阶段 2
② 感知单独运行以 skip_planner:=true 启动感知，读取 /targets_3d方块坐标必须落在 pick_zone 区间内。三个轴均需检查，不满足时检测结果会被静默丢弃
③ 小幅度运动夹爪一次开合，单关节转动 ±5°，完成后回到原位轨迹返回 status==SUCCEEDED 且 error_code==0
④ 完整抓取启用规划器见 §8

7. 仿真环境

仿真仅运行在开发机（WSL）上，上位机未安装 Gazebo。启动方式：

source /opt/ros/humble/setup.bash
source <gz_ros2_control 所在工作空间>/install/setup.bash    # 需以 GZ_VERSION=harmonic 编译
source ros2_ws/install/setup.bash
export PYTHONPATH=<venv>/lib/python3.10/site-packages:$PYTHONPATH   # 提供 torch/ultralytics
ros2 launch arm_grasp_sim full.launch.py headless:=true

rclpy 位于 ROS 环境，torch 位于 venv，两者互不可见，需在运行时叠加。构建时不叠加 venv，否则 colcon build 会因 setuptools 版本差异失败。

仿真场景采用仿真几何（台面位于 base_link z≈−0.39，方块位于 +x 侧），与真机不同。其用途为验证状态机与运动控制逻辑，位置相关的验证必须在真机上进行。

8.1 夹爪回读值的含义

回读值含义
接近全开（如 95 mm）夹爪未动作，指令未写入或未初始化
0 mm到达闭合位，钳口之间无异物
中间值（如 35 mm）已夹持物体，无法到达闭合位

因此上述“等手指到位超时”的告警在出现中间值时表示抓取成功。

8.2 收工路径

触发条件日志
抓取区无候选空闲 Ns 没有发起过任何一次抓取尝试
槽位用尽收工：放置槽位已用尽（N 个）—— 没有地方可放了
连续无进展连续未放置 M/10（由 max_attempts_without_place 控制）

9. AG-95 寄存器

寄存器读写含义
0x0100只写初始化命令（0x01 单向，0xA5 全行程）。读回值恒为 0，不可用于判断状态
0x0101写夹持力（45~160 N）
0x0103写目标位置（0–1000 千分位）。读回值为上一次写入的目标
0x0200只读初始化状态：0 未初始化，2 初始化进行中，1 已完成
0x0201只读到位状态
0x0202只读实时位置（0–1000 千分位）：0 全闭，1000 全开

写入位置指令前须读取 0x0200 并确认其值为 1，值为 0 或 2 时应拒绝执行。gripper.py 已实现该检查，检查位置在 dry-run 分支之后，以保持 dry-run 模式下串口零流量。

初始化过程为全行程自检，包含张开与闭合两个方向。执行前需确认两指在整个行程范围内无遮挡物。

读回值非 0 才能证明该地址为有效寄存器：该从站对不存在的地址同样返回 0。

现象检查项
示教器播放程序时报连接被拒绝驱动是否已启动（ss -lntp | grep 5000）。启动顺序应为先驱动后播放
机械臂运动到关于基座对称的位置相机外参的父坐标系是否为 base 而被当作 base_link 使用（§4.1）
夹爪无动作且回读值恒为全开ag95_dry_run 是否为 true；0x0200 是否为 1
夹爪报告成功但未动作未初始化状态下位置回读恒为 0 导致的误判（§9）
规划器无任何动作且日志无输出方块未落入 pick_zone，该筛选失败时无日志
可抓取但无法放置，下降段 IK 被拒place_z 是否按几何中心而非顶面计算（§4.4）
包线扫描结果为“一个位姿都没解出来”缺少 robot_state_publisher。应使用 no_arm_stack.py，而非单独以 start_ur_driver:=false 启动
ros2 topic list 或 action list 返回空或超时ROS CLI 守护进程响应问题。可使用 --no-daemon 或延长等待时间，与链路状态无关
修改配置文件后无效果确认启动的 launch 实际加载的是哪一份配置文件（§5）
