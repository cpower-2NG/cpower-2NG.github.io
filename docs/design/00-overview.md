# BIFROST 设计文档 · 总览

> 本文是整套设计文档的入口与全局决策记录。
> 推荐阅读顺序：`00-overview` → `10-data-design` → `20-backend` → `30-frontend` → `40-migration-ops`。

## 目的

BIFROST 是一个个人知识界面：以内容（文章与动态）为中心，在 Logic 与 Fantasy 两个位面之间承载阅读、记录与展示。

这套设计文档的职责，是把"内容如何组织、如何存储、如何被检索、如何被呈现"固化成一套可以直接实现的规格，避免实现过程中反复漂移。

## 范围

### 本轮范围

- 设计一套以文章与条目为中心的数据库架构。
- 定义内容模型、分类体系、存储组织与检索方案。
- 定义后端与前端的职责边界与契约。

### 非目标

- 本轮只产出设计文档：不改代码、不改视觉、不动线上静态站。
- 不讨论具体视觉样式与组件细节。
- 不做多用户与权限体系。

## 术语表

术语只在本节定义一次，其余文档只引用、不重新定义。

| 术语 | 含义 |
|---|---|
| phase 阶段 | 站点的两个身份相位：`logic`（技术档案）与 `fantasy`（阅读回廊）。决定视觉气质与默认内容。 |
| section 分区 | 阶段下的稳定入口，构成侧栏骨架。数量少、长期不变。 |
| tag 标签 | 自由输入的主题或作品名标记，可组合筛选、可自动生成标签页。 |
| series 系列 | 有顺序的合集实体，例如"纸上魔法使 1–5"。 |
| kind 形态 | 内容的展示形态，例如普通长文、出版物、视频条目、项目、页面。 |
| entryId | 条目的稳定唯一标识，永不变更。 |
| slug | 条目的可读地址片段，可以修改。 |
| path | 条目当前的访问路径，可以修改；由 `routes` 负责解析与重定向。 |
| 条目 Entry | 内容的概念单位。文章、动态、项目、页面在概念上都是条目，物理上可以分容器存储。 |
| 动态 moment | 短内容时间流，来源为 QQ 同步、网页手写与转发视频链接。 |
| 检索投影 | 为检索服务准备的扁平只读记录，是权威内容的派生，不是权威数据。 |
| 展示页 | Logic 首页，工作记录展示页，内容为简介、技术栈、项目与工作记录。 |
| 系列卡片 | 系列在列表中呈现的那张卡片；点开后显示系列成员，默认第一篇。 |

## 关键决策

### 设计原则

- **内容优先**：数据库是内容的唯一权威；Git 退为源码仓库与发布快照。
- **单一归属**：一个事实只在一份文档定义；其余文档只链接，不复制。
- **读写分离**：权威存储负责写入，检索层负责列表、筛选、搜索与分面。
- **身份与地址解耦**：`entryId` 永不变，`slug`/`path` 可改，旧地址靠重定向兜底。
- **生命周期分层**：原件永久保存、派生媒体可重建、限流数据自动过期。

### 决策记录

状态取值：`已定` / `待补充`。

| 编号 | 决策 | 理由 | 状态 |
|---|---|---|---|
| D-01 | 数据库成为内容的唯一权威，Git 退为源码与发布快照 | 内容集中到数据库才便于查找与迁移 | 已定 |
| D-02 | 内容入口为"上传文件"与"网页写动态"，编辑器后置 | 上传成品文件与随手写动态是两种真实场景 | 已定 |
| D-03 | 源文统一转 Markdown，与渲染 HTML 双存 | 保留可编辑源，兼顾再渲染与前端展示 | 已定 |
| D-04 | 上传原件（Word / PDF / txt）长期保存到私有 Blob | 转换会丢信息，原件是迁移与重做的安全网 | 已定 |
| D-05 | 媒体独立建库并被条目引用 | 便于查重、复用与独立迁移 | 已定 |
| D-06 | 媒体分原件与派生品两类 | 原件不可再生，缩略图与视频封面可随时重建 | 已定 |
| D-07 | 视频只存引用，封面由服务端派生 | 视频文件不入库，封面不是需要人工维护的资产 | 已定 |
| D-08 | 文章与动态分容器存储，概念上统一为条目 | 两者访问模式与数量级不同，但共享身份、检索与互动 | 已定 |
| D-09 | 动态永久保留并按月分桶 | 动态持续增长，按月组织可让"翻最近"只碰少数分区 | 已定 |
| D-10 | "日常"分区就是纯时间流动态，不存在独立的手记/短篇 | QQ 同步、手写动态、转发链接是同一类内容 | 已定 |
| D-11 | 系列是独立实体，带顺序与合集介绍 | 需要专题页与可控顺序，标签做不到 | 已定 |
| D-12 | 分类法入库、可管理，不写死在代码里 | 分类会长期演进，改分类不应改代码 | 已定 |
| D-13 | 检索采用 Cosmos + Azure AI Search 两层 | Cosmos 不擅长任意维度组合与全文检索 | 已定 |
| D-14 | 所有条目在写入时生成统一的检索投影 | 单一索引来源，分页、排序、分面才准确 | 已定 |
| D-15 | 发布形态为"静态物化 + API 检索" | 阅读快、SEO 好、Azure 不可用时仍可读 | 已定 |
| D-16 | 正文保留历史版本 | 内容最核心，误改要能回滚 | 已定 |
| D-17 | 网址用稳定 entryId + 可读 slug，旧地址重定向 | 改标题不丢评论与外部链接 | 已定 |
| D-18 | 上传后的转换在异步导入任务中完成 | 大文件（如 60MB PDF）不应阻塞请求 | 已定 |
| D-19 | 迁移采用双轨过渡 | 新库先跑通并验证，旧静态站继续可用 | 已定 |
| D-20 | 保持单用户模型，只保留 author 展示字段 | 没有多用户与权限需求 | 已定 |
| D-21 | 来源信息不面向用户，仅保留开发者技术溯源 | "来源：上传 / QQ"对读者无意义，只用于排查 | 已定 |
| D-22 | 分区与主题细分分离，评论/随笔/翻译等降为标签 | 主题会不断增长，分区必须少而稳定 | 已定 |
| D-23 | 侧栏只放结构导航，永不展开具体条目 | 内容变多时侧栏不应膨胀 | 已定 |
| D-24 | 查找入口为搜索框 + 组合筛选 + 分面计数 | 需要按类型、分类、标签、时间多维查找 | 已定 |
| D-25 | 自动生成分类页、标签页、系列页、年份归档页 | 提供浏览与内容发现入口，并利于 SEO | 已定 |
| D-26 | Logic 首页即展示页：简介 + 技术栈 + 项目 + 工作记录 | 工作展示是 Logic 位面的主要功能 | 已定 |
| D-27 | 标签自由输入并自动登记，可重命名与合并 | 既要随手打 hashtag，又要避免重复与错字 | 已定 |
| D-28 | 设计文档拆为 5 份并遵循单一归属 | 避免同一事实在多处描述后各自过期 | 已定 |
| D-29 | README 降级为项目入口 | 原 README 同时承担简介、设计、手册、验证四种角色 | 已定 |
| D-30 | Fantasy 分区定名为 日常 / 漫评 / 活动纪录 / 杂记 / 档案馆 | 功能名可读但过风格化，改成平实命名 | 已定 |
| D-31 | Logic 分区定名为 展示 / 技术文档 / 心得 / 算法，展示即首页 | 工作展示是 Logic 位面的主要功能 | 已定 |
| D-32 | 系列在列表中表现为一篇文章，打开显示成员并默认第一篇 | 系列既要有合集页，也要能作为入口被浏览 | 已定 |
| D-33 | 位面切换与搜索分离：`~` 只切位面，`Ctrl/Cmd+K` 打开搜索面板 | 位面切换是彩蛋式设计，与检索职责不同 | 已定 |
| D-34 | 文章分区列表用杂志式（首篇大图 + 卡片） | 纯列表过于普通，杂志式有层次且不呆板 | 已定 |
| D-35 | 日常分区用社交动态流（无头像、正文 + 时间 + 错位图片 + 视频卡 + 互动） | 日常是时间流场景，形态应贴近社交动态 | 已定 |
| D-36 | 封面兜底：指定封面 → 正文首图 → 文字封面 | 现存内容多无封面，列表不能因此显得空 | 已定 |
| D-37 | 标签只出现在搜索面板，标签页支持可选简介 | 标签是检索维度，不应占用侧栏 | 已定 |
| D-38 | 系列带封面与简介、动态带置顶与精选、标签带可选简介 | 三者都需要作为可浏览对象被展示 | 已定 |
| D-39 | 项目条目字段：名称、简介、封面、技术标签、仓库/演示链接、状态、起止时间 | 满足展示页需要且不引入过度维护 | 已定 |
| D-40 | 展示页字段：简介、名片图、技术栈分组、工作记录时间线 | 覆盖简介 + 栈 + 项目 + 记录四个板块 | 已定 |
| D-41 | AI Search 用 `japaneast` 免费层起步 | 与现有资源同区域，先用免费层验证 | 已定 |
| D-42 | 导入任务复用现有 Container Apps Job | 已有执行载体，不引入新的队列服务 | 已定 |
| D-43 | 索引器在发布后显式触发，另有每日补偿刷新 | 保证新内容及时可搜，同时兜住漏触发 | 已定 |
| D-44 | docx 保真验收：段落数、标题数、列表项数、图片数四项计数一致 | 格式无法完全保留，但结构必须可校验 | 已定 |
| D-45 | CI 新增导入与检索相关 workflow，旧 Pages 流程保留至切换完成 | 双轨期两侧都要能跑 | 已定 |
| D-46 | 编辑器只预留写入接口，不做界面 | 网络编辑本期不做，但数据路径要先通 | 已定 |

## 接口与契约

本节只定义"文档之间的契约"，具体数据契约由各归属文档定义。

- **单一归属**：一个事实只在一份文档定义，其余文档只链接、不复制。
- **统一模板**：每份文档固定使用"目的 / 范围 / 关键决策 / 接口与契约 / 开放问题"。
- **留空约定**：尚未充分讨论的部分用 `> 待补充：…` 标注；本轮有意推迟的部分用 `> 留待后续阶段讨论：…` 标注。两种情况都不臆造内容。
- **快速开始归属**：本地预览与验证的命令写在 `README.md`；脚本行为与边界规则写在 `40-migration-ops.md`。
